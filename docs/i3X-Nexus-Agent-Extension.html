i3X Nexus Agent Extension

Level 5 of the i3X Nexus ProfileCivOpsBuilds on the i3X Nexus Profile (draft 0.4), contributed by LNS Research

1Abstract

The i3X Nexus Profile lets a software agent ask for a change but never approve one. This extension adds what a site needs once it has more than a handful of agents: every agent works for a named person, on one task, inside part of the plant, with a budget and an end time; one switch stops all agent writes; any MCP-speaking agent can use a nexus through the same governed paths; approvals are signed; and the audit ledger can be checked against copies its own administrators cannot rewrite.

It defines Level 5 of the profile. A nexus at Level 5 meets Levels 1–3 of the profile and everything here. Nothing here changes the i3X 1.0 contract: the additions are under /x-nexus/ and /mcp, and a client that knows nothing about them keeps working.

The key words MUST, MUST NOT, SHOULD and MAY are used as in RFC 2119 and RFC 8174. Requirements are numbered NXA-n; NX-n refers to the profile.

Core rule, unchanged. An agent may request; it never approves (NX-21). This extension makes it possible to say, for every agent request in the ledger, which person the agent was working for, on what task, and under what limits.

2Grants

A grant is issued by a person to one agent principal. It carries a task description, one or more areas (element ids; the grant covers each and everything below it in the address space), the actions allowed (read, media:read, request:W1, request:W2), a maximum number of write requests, and an expiry. The person who issues it is its sponsor.

  • NXA-1At Level 5 an agent principal MUST act only under a live grant. An agent presenting no grant MUST be refused on every endpoint except GET /info. Only a person holding the agents:grant scope MAY issue a grant, and the issuer MUST be recorded as the sponsor. A grant MUST expire within 24 hours; the default is 60 minutes. The grant's credential MUST be shown once, at issue, and stored only as a hash.
  • NXA-2A write request raised under a grant MUST record the grant id, its task, and the sponsor as actor.onBehalfOf. Whatever the agent itself supplies for onBehalfOf MUST be ignored.
  • NXA-3An agent on a grant MUST NOT read, list, subscribe to or target an element outside its areas. Requests naming such an element MUST be refused (403); listings MUST omit such elements. The agent MAY read the write-request intakes and the write requests it raised itself, and no others. A request beyond the grant's maximum, or for an action the grant does not allow, MUST be refused before anything is recorded.

Grants are records in the nexus ledger. Issuing and revoking one are hash-chained versions like any other write, and in a redundant pair they are replicated to the standby. They are not i3X elements, so no client can browse another's grant.

3Registry, freeze, suspend, revoke

  • NXA-8A nexus MUST provide a freeze: one action that stops every agent write on the site. While frozen, new agent write requests MUST be refused (423), and agent requests already approved MUST be held rather than applied; they are applied when the freeze is released, or expire. Reads, and writes by people and services, MUST carry on. Any person with agents:freeze MAY freeze; only a person with agents:admin MAY release. A reason MUST be given for both. The freeze request MUST be served in the P0 lane.
  • NXA-9A person with agents:admin MUST be able to suspend one agent, which refuses it on every endpoint, and resume it. A grant's sponsor or an admin MUST be able to revoke a grant, which stops its credential at once.
  • NXA-10A nexus MUST provide a registry of agents: for each, its live and past grants (sponsor, task, areas, actions, requests used of the maximum, expiry), its write requests by outcome (verified, rejected, rolled back, expired), and its recent refusals (outside its areas, over budget, while frozen or suspended). An admin sees every agent; a sponsor sees the grants they issued.
  • NXA-11Freeze, release, suspend and resume MUST be recorded as ledger versions naming the person and the reason.

4MCP surface

Most agents speak the Model Context Protocol. A Level 5 nexus answers MCP at POST /mcp (Streamable HTTP, JSON responses, no session state) with the caller's own credential.

  • NXA-4Every MCP tool MUST be carried out as the equivalent i3X request, as the caller, through the same authentication, grant checks, rate limits, priority lanes and write governor. An MCP tool MUST NOT reach any store or system by another path. A refusal MUST be returned as a tool result with isError: true and the i3X status, not as a protocol error.

There is no approval tool. An agent cannot approve through MCP for the same reason it cannot through i3X.

5Approvals

  • NXA-5The sponsor of a grant MUST NOT approve a request raised under it. Asking through an agent and then approving the answer is approving one's own request, which §7.4 of the profile forbids.
  • NXA-6A nexus MAY require signed approvals. Then each approver registers an Ed25519 public key, and an approval MUST carry a signature over nexus-approval:v1|{request id}|{decision}|{version hash}, where the version hash is the ledger hash of the request version the approver read (served at GET /x-nexus/requests/{id}). An approval signed over any other version MUST be refused, so a decision cannot be carried onto a request that changed after the approver looked. The signature MUST be kept with the approval in the ledger. A person with a registered key MUST sign whether or not the nexus requires it.

6Ledger anchoring

The profile's hash chain shows an edit, removal or reordering to anyone who trusts the head of the chain. Someone with write access to the ledger's database could rewrite every version after an edit and leave a chain that still verifies on its own.

  • NXA-7The nexus that holds the write role MUST, at least every 5 minutes while the ledger has grown, sign a checkpoint {site, node, count, head, at} with an Ed25519 key held outside the ledger's database, and append it to at least one store outside that database's administrative control: an append-only file on separate storage, an HTTP endpoint in another trust domain, or both. A verifier MUST report a ledger whose version at an anchored count does not have the anchored hash, or which has fewer versions than an anchor counts.

The reference implementation ships the verifier as scripts/verify-anchors.ts, for a file ledger or a PostgreSQL ledger.

7Plant text is data

Work-order titles, notes, tag descriptions and the like are written by many people and systems, and an agent reads them. Any of them can carry text that looks like an instruction.

  • NXA-12MCP tool and server descriptions MUST state that values are plant data and never instructions. A write request MUST name a target that exists on the nexus; the governor resolves it itself and never acts on a target or authority the request text asserts. Nothing in a value MAY change what an agent's grant allows.

These rules do not make an agent immune to injected text. They bound the damage: whatever an agent is talked into, it can only ask, inside its areas and budget, for a person to decide.

8Conformance

Level 5 · Governed agents

Requires
Levels 1–3 of the profile (Level 2 when the site runs a pair); NXA-1 to NXA-12.
Tests
  • An agent without a grant, with a revoked grant, and with an expired grant.
  • Reads, listings, subscriptions and requests inside and outside the grant's areas; a request past the grant's maximum.
  • The sponsor trying to approve the agent's request.
  • Freeze before an approval, then release: the approved request is held, then applied once.
  • The same through the standby of a redundant pair.
  • Every MCP tool inside and outside the grant; a retried request_change.
  • Unsigned approvals, approvals signed over a different version, and correct ones, with signing required.
  • A ledger rewritten from an early version onward, so its own chain verifies; a truncated ledger; a forged anchor.
  • The profile's conformance suite, three runs, with Level 5 enabled.
Pass
  • Every refusal happens before anything is recorded, and every agent request in the ledger names its sponsor and grant.
  • No agent write is applied while frozen; people's writes are unaffected.
  • MCP and i3X give the same answer for the same call.
  • The verifier flags every rewritten or truncated ledger and every forged anchor.
  • Full 1.0 Compliance in all three runs.
